# FactorySim benchmark 2.0

A suite of multi-robot factory instances for planning, scheduling and reinforcement learning. Every instance is a
JSON file with the factory configuration, the orders, the simulator settings and ground truth, generated by
`factory-sim generate` (suite `factorysim-2.0`). `index.json` records the code version that generated the suite;
`factory-sim verify --suite benchmarks/v2.0` checks that your installed code reproduces the stored ground truth.

Suite 2.0 is built on the people-free reference lab (`lab.yaml`): TurtleBot3 robots with an OpenMANIPULATOR-X arm pick,
carry and place every tray, and kitting, assembly and inspection run as timed station processes (no operators, no
technician). The 1.x suites used the lab with a human workforce; they are kept and regenerate exactly from
`lab_v1.yaml` (`factory-sim generate --version 1.0` or `1.1`).

## The task

Arm robots carry trays between stations; a dispatcher releases orders. Decide releases, pickups, deliveries, moves,
charging and machine changeovers so that all orders finish soon and on time. Durations, breakdowns, robot faults,
rejects and jams are random (seeded); everything else is deterministic.

## Families

Each family fixes some of 17 dimensions; the rest keep their base values (fixed routes, medium contention,
stochastic durations, finite buffers, batch arrivals, dock queues, loose deadlines, no disturbances, arm robots).
Families marked *1.x* need people (operators with breaks, or human tray handlers) and are not in suite 2.0; they can
still be generated by name (`--families`), and the workforce is then added to the lab.

| Family | What it tests |
| --- | --- |
| `base` | the reference lab as specified |
| `independent` | low contention, unlimited buffers: mostly a routing / transport problem |
| `bottleneck` | products concentrated on shared machines |
| `flexible`, `alt_machines` | route choice / alternative machines per step |
| `congested` | dock queues and slowdowns from robot traffic |
| `breakdowns` | machine failures (MTBF / MTTR) |
| `online` | orders arrive over time (Poisson) |
| `blocking` | no output slots or overflow buffer: deadlock-prone |
| `quality`, `scrap` | inspection rejects with rework, or scrap and re-order |
| `noisy` | twice the duration noise |
| `tight`, `rush`, `infeasible` | tight due dates, weighted rush orders, deadlines that cannot all be met |
| `exact` | deterministic, unlimited buffers: CP-SAT proves optimal makespans |
| `charging` | batteries with random initial charge, auto-charging, two shared chargers |
| `robot_faults` | robots stop for repairs |
| `maintenance` | preventive services and a planned window |
| `reconfig` | machines can be re-tooled to take over a broken machine's role (changeover decisions) |
| `breaks` (*1.x*) | operators leave for breaks |
| `shortage` | raw-material kits run out and are replenished |
| `jams` | conveyor jams |
| `full` | many dimensions at once |
| `disturbed` (2.0) | every disturbance that involves no people: breakdowns, online arrivals, rework, rush orders, batteries, robot faults, maintenance, reconfiguration, shortages, jams |
| `realistic` (*1.x*) | every disturbance, with the workforce and operator breaks |
| `tray_fleet` (*1.x*, 1.1) | TurtleBot3 tray robots without arms: human handlers move the trays (handover actions, handler waits) |
| `mixed_fleet` (*1.x*, 1.1) | arm robots + tray robots (+ a Burger on L): heterogeneous speeds, times and actions |

Suite **factorysim-1.1** (`factory-sim generate --version 1.1`) is 1.0 plus the two fleet families; the 1.0
instances are unchanged (same seeds, configs and ground truth). Robot types: `factory-sim robots`.

Sizes: S (2 robots, 4 orders), M (3, 8), L (4, 14). Splits: train (S, M; 50 per family and size), val (S, M; 10),
test (M, L; 10, larger than training). `exact`: S only.

## Ground truth per instance

- `lower_bound`: max of per-order flow, per-machine (pooled under reconfiguration) load, robot transport work /
  robots and operator load (1.x); on the test split's M instances also the CP-SAT relaxation bound (`cpsat.bound`).
- `best_known`: best makespan known (rules in nominal mode, CP-SAT optimum on `exact`).
- `reference_makespan` / `reference_policy`: best rule in nominal mode.
- `infeasible_deadlines`: some due date is earlier than that order's own minimum flow time.

## Metrics and reporting

Report, per family and size of the **test** split, over 3 seeds per instance:

1. success rate, and deadlock / stall rate;
2. makespan / `lower_bound` and makespan / `best_known` (successful runs);
3. on-time rate and (weighted) tardiness;
4. decision time per run.

`factory-sim bench --suite benchmarks/v2.0 --split test --policy <policy>` computes all of these and writes one JSONL
row per run. Report the `exact` family's gap to the CP-SAT optimum separately. Train only on `train` (and tune on
`val`); never on `test`. State the code version (`factory_sim.__version__`) with your results.

## Interfaces

The same instances can be used as a Gymnasium env (`FactorySim-v0`, masked `Discrete` actions, fixed-size
observation for every instance), a PettingZoo AEC env (dispatcher + robots), a PDDL 2.1 problem
(`factory-sim pddl`), a CP-SAT scheduling model (`factory-sim solve`) or a Gazebo / ROS 2 twin (`factory_sim/ros`).
